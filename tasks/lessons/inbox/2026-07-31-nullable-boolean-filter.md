## A nullable boolean filter must admit NULL — `.eq(col, false)` silently excludes every active row (2026-07-31)
`groups.archived` is NULLABLE, where **NULL means active** — only explicitly-archived rows carry `true`. So the dedup lookups in `app/actions/auto-chats.ts` needed `.or("archived.is.null,archived.eq.false")`; a plain `.eq("archived", false)` would have matched only rows someone had explicitly written `false` into, excluding every genuinely-active chat and INVERTING the bug being fixed (dedup would then never find the live row and would create a duplicate every time). Three-valued logic is the trap: in SQL `NULL = false` is NULL, not true, so the row is filtered out. Before filtering on any boolean, check its nullability and whether NULL is a meaningful state — if NULL is the default/active state, the filter must name it. Same shape applies to `.neq()`, which also drops NULLs.

**Corollary — scope a dedup filter to READS only.** The same commit deliberately did NOT apply the filter to: the archive actions themselves (they SET `archived = true`, so filtering them out is self-defeating), any INSERT, the UPDATEs by id, or the explicit-id lookup. Only name/link *convergence* paths need it. A filter that leaks onto the write that sets the flag breaks the feature it was added to protect — when adding a guard to reads, enumerate the write paths and say explicitly why each is excluded (that commit's message does; copy the habit).
